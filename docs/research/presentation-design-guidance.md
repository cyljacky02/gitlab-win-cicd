# 跨部門 Windows 部署治理提案：簡報設計研究

## 結論與適用範圍

以「**開發交付版本，授權部署流程控制上線**」為核心訊息；讓非開發同仁看懂誰提出、誰核准、誰執行、失敗由誰處理，而不是學會工具架構。採 **12 頁、無附錄、真正封面、每頁一個訊息**。

以下將來源原則與本案設計建議分開。GitLab Runner 直接送檔方案「已否決」、Rundeck／Azure DevOps（ADO）為授權 CD 候選，是本次研究的題設，**不是這些設計來源證實的產品限制或公司政策**。核准權、部署帳號、稽核與復原能力仍需依實際設定確認。

## 來源支持的設計原則

- **從聽眾需求出發。** Duarte 主張以聽眾為主角，而非產品或講者；本案應先談上線風險、責任與決策，再談工具。[1]
- **一頁一個意思。** Duarte 建議單一訊息，並以約三秒可辨識主旨的 Glance Test 檢視；三秒是設計檢查目標，不代表觀眾須三秒讀完流程。[2]
- **少字、穩定版式。** TED 建議先思考內容、使用一致樣式、避免把講稿搬上投影片；過多文字會讓閱讀與聆聽互相競爭。[3]
- **用大小、對比、留白建立層級。** Duarte 建議以視線流向、尺寸／形狀／色彩／距離的對比與留白突出重點。[2]
- **可讀性不能只靠顏色。** Microsoft 建議每頁唯一標題、足夠對比、不以色彩作唯一訊息、18pt 以上無襯線字及留白；並檢查替代文字與閱讀順序。[4]
- **封面可獨立存在。** PowerPoint 官方提供獨立 Title Slide 版型；此來源支持版型用法，不規定本案封面內容。[5]
- **責任用泳道表示。** draw.io 官方說明：依團隊責任分組流程步驟，可使交接與責任更易理解，適用於跨部門流程與專案核准。[6]

## 本案建議的 12 頁敘事

以下頁數、標題與圖形是研究綜合建議，並非來源要求；不要另插目錄頁或附錄。

| 頁 | 標題／唯一主旨 | 主要畫面 |
|---|---|---|
| 1 | **Windows 部署治理提案** | 真正封面：副標「從開發送檔，轉為授權上線」、提案單位、日期；不放比較表、流程或技術清單 |
| 2 | **今天要決定：是否採用授權部署流程** | 決策一句話；標明已否決方案不再尋求核准，工具選型另行確認 |
| 3 | **直接送檔無法滿足本案上線權責要求** | 已否決路徑簡圖；只列已確認的治理落差，不泛稱 GitLab 天生不安全 |
| 4 | **交付版本與准許上線，是兩件不同的事** | 「開發交付」與「授權部署」兩個區塊，中間標示權責邊界 |
| 5 | **推薦：由授權 CD 流程執行上線** | 白話流程「準備版本 → 提出申請 → 核准 → 部署 → 驗證／留存紀錄」；CD 首次解釋為部署流程 |
| 6 | **每次上線都有人核准、有人負責** | 開發、核准者、部署維運三條泳道；正式角色名稱待組織確認 |
| 7 | **未核准就停止；部署失敗就進入復原流程** | 小型例外流程，標示未核准、驗證失敗、通知與復原負責人 |
| 8 | **方案差別在上線控制，不在送檔速度** | 已否決／推薦兩張對照卡：誰可執行、核准在哪、紀錄在哪、誰負責復原；未知項標待確認 |
| 9 | **Rundeck 或 ADO 都必須符合相同治理條件** | 相同條件的兩張候選卡；避免做未驗證的產品能力排名；兩者是替代候選，不暗示必須串接 |
| 10 | **先驗證核准、追溯與復原，再擴大使用** | 三個試辦驗收情境：未核准不能上線、版本與執行者可查、失敗可按核定方式復原 |
| 11 | **導入需要跨部門確認責任與資源** | 三組工作卡：開發交付、核准規則、維運執行；列負責單位與待確認時程，不虛構承諾 |
| 12 | **請核定治理方向、試辦範圍與責任窗口** | 明確決策清單與下一步；不要只有「謝謝」 |

## 視覺與文字規格建議

- 內容頁採「結論式標題 → 一張主圖 → 一句意義／決策」；不用「系統架構」「方案比較」等只有分類、沒有訊息的標題。[2]
- 本案可先採標題 32–40pt、正文與圖中文字 24–28pt；Microsoft 的 **18pt 是來源建議下限**，不是投影流程圖的理想尺寸。若必須縮字，先刪步驟或跨既定頁面分配內容。[4]
- 使用繁體中文無襯線字型（如微軟正黑體），固定標題位置、對齊與間距；一頁優先一張圖或最多三組短句。這是本案實作起點，不是硬性通則。[2][3][4]
- 推薦／否決用**文字標籤＋形狀或線型＋顏色**；不要只用紅綠。保留足夠明暗對比，避免淡灰小字與裝飾背景。[4]
- 第一次標示「GitLab Runner（開發自動化執行工具）」「CD（部署流程）」「ADO（Azure DevOps）」；後續圖中以「準備版本」「核准上線」「執行部署」等動作為主。不要展示 YAML、命令、路徑或憑證名稱。[1][2]

## 流程／泳道的畫法

- 主流程建議左到右，約 5–6 個步驟；方框＝工作、菱形＝決策。箭頭代表交接／順序而非網路連線；跨泳道箭頭標「提交版本」「提出申請」「授權執行」。加小圖例，讓非工程觀眾無須猜測符號。[6]
- 將人員核准節點明確放在 Windows 部署之前。菱形兩條出口寫「核准」「不核准」；失敗分支寫「驗證失敗 → 通知負責人 → 依核定程序復原」。不要把成功路徑與所有例外塞在同一圖。
- 同一個「Windows 正式環境」在比較圖使用相同位置與大小；已否決路徑標「不採用」，推薦路徑標「需核准」。責任泳道用角色／部門命名，工具名稱放在步驟的次要文字。
- **Mermaid 適合可版控的簡單流程草圖。** 官方支援 `flowchart LR`、節點、箭頭文字、菱形與 `subgraph`；Unicode 標籤應以雙引號包住。**subgraph 不等同固定泳道排版**：內部節點連到外部時，其方向設定會被忽略並繼承主圖方向；跨責任流程須實際檢查輸出，不可假設能固定泳道。[7]
- **需要精準泳道與人工調整時用 diagrams.net／draw.io。** 保存可編輯 `.drawio` 原檔，再輸出供簡報使用。PNG 匯出只有勾選 **Include a copy of my diagram** 才能保留可重新匯入 draw.io 編輯的圖資料；此可編輯性**不代表 PowerPoint 中每個圖形都是原生可編輯物件**。解析度／縮放也需配合投影片尺寸檢查。[6][8]

## 完稿檢查

1. 只看 12 個標題，能否說出「為何改變 → 如何控制 → 誰負責 → 請核定什麼」？[1][2]
2. 讓非開發同仁看圖，能否指出誰核准、誰部署、未核准會怎樣、失敗找誰？[6]
3. 投影尺寸下，圖中最小文字仍可讀；縮圖能辨識主旨，灰階仍能辨識方案狀態。[2][4]
4. 執行 PowerPoint 無障礙檢查，確認唯一標題、閱讀順序、圖的替代文字與文字對比；圖片內文字仍需人工檢查。[4]
5. 政策、工具能力、角色、時程與試辦驗收經負責人確認；不將「使用某產品」等同「自動取得治理」。
