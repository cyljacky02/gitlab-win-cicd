## 5｜自動化部署：比較三種做法，選定 Azure DevOps

比較過三種做法。一、GitLab Runner 直接部版：最簡單，但等於開發端可直接操作正式主機，10/8 被其他部門否決。二、Rundeck 拉取已建置的版本再部署：POC 可行。三、Azure DevOps Server：從數開得知他們已在使用 Azure DevOps，它也是未來專開部規劃導入的方案之一；Agent 裝在目標機上主動向 Server 取工作，對 Windows 環境的原生支援也比較好，因此評估後認為 ADO 比 Rundeck 更適合。正式導入時，ADO 放行後由 Agent 呼叫 WinCD 換版。

## 6｜POC：GitLab → ADO → Windows 全流程已跑通

POC 以隔離的 GitLab 專案真 push 觸發，不是手動排 ADO。本地與遠端兩階段各跑 main 與 production 路線：main 全自動；production 有部署前與導流前兩道核准，觸發者不可自核。另外驗證健康檢查失敗自動還原舊版、指定版本退版、來源與 SHA-256 檢查。POC 的核准是代理執行的自動化核准；只驗完整 IIS 站台與模擬導流意圖，沒有 F5／真實網路排空、多台主機、reboot／kill 實測，這些列在正式環境驗證。

## 8｜WinCD：人工與 Runner／Agent 共用的換版工具

WinCD 是 Windows 換版工具。部署人員在主機上用繁體中文 TUI；GitLab Runner 或 Azure DevOps Agent 用 wincd 指令，例如 wincd deploy。三種入口呼叫同一個換版引擎、使用同一份 release。審核與多台主機的先後順序在呼叫工具之前由 GitLab／ADO 完成，WinCD 只負責在單台主機上執行。每次換版固定走：Down F5 → 停止服務 → 備份 → 寫入 → 啟動服務 → 檢查 → Up F5（可設定自動或核准後才導流）；中途失敗會還原檔案與服務的原始狀態。

## 9｜WinCD 功能重點：一份設定，換版、退版、復原都有紀錄

功能重點：一、部署設定是三個 YAML（wincd.yaml、mappings.yaml、operations.yaml），跟著每台主機的分支版控。二、目錄與檔案對應先比對 SHA-256，只寫有變的檔案，備份只含會被覆蓋或刪除的檔案；目錄可選疊加或完整同步。三、F5 導流：換版前 Down，就緒後 Up，可設定自動或等 pipeline 核准後再 Up。四、保留最近幾個版本，可一行指令退版。五、換版被中斷（Ctrl+C、斷線、當機）可偵測並執行復原。六、每次換版留紀錄，-Json 與 exit code 方便 pipeline 判斷。目前測試環境驗收已完成；正在進行真機驗收、目錄對應的 Update／Delete；後續有 TUI 介面優化與歷史退版設計。
